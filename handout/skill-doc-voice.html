Summary

Docs that read like marketing copy or dry internal prose get rewritten — problem-first, proof-led, no fluff. Governs how the prose reads; structure is /documentation-standard's job.

When to use

The reader is a developer deciding whether to install, try, or trust a tool. They are skeptical, fast-scanning, and one tab-close away from leaving. Use /doc-voice when writing or revising any user-facing prose meant to convince that reader.

Trigger phrases (from SKILL.md):

  • "improve this README"
  • "rewrite the docs"
  • "make this clearer"
  • "remove the marketing fluff"
  • "landing copy"
  • "user manual"
  • "write a handout"

Not for: code comments, commit messages, ADRs, or internal specs — those have different voice constraints.

Invocation

Invoke directly, then paste the copy to rewrite or describe what to write:

/doc-voice [paste existing copy or describe what to write]

The skill rewrites or drafts in one pass. For a deeper adversarial check of the result, follow up with /da-review.

Example 1 — Killing marketing language

Input:

/doc-voice
Supercharge your workflow with our powerful AI-driven code review tool!
Seamlessly integrates into your development process and effortlessly
catches bugs before they reach production.

Output / Result:

Code review that finds real bugs — not style preferences.
One command, seven check groups, 85 automated detections.
Runs on local changes, a git range, or specific files.

Example 2 — Pain-first feature bullet

Input:

Write a feature bullet for /plan-maker that doesn't sound like marketing.

Output / Result:

- **/plan-maker** — Stop staring at a ticket wondering where to start.
  Breaks a feature brief into the smallest tasks with tests and
  dependencies — ready for /implement-next to chew through.

Related tools

  • /documentation-standard — Structure, organisation, and naming conventions for docs. Use it first to get the shape right; then /doc-voice to fix how it reads.
  • /da-review — Adversarial one-pass review of the output. Run it after /doc-voice to catch claims that don't hold up.
  • /aaa — Benchmarks the output against world-class examples and names specific upgrade paths. Use when "is this good enough?" is the question.
