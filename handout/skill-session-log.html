What it is

/session-log keeps a running record of your coding sessions. While it is on, every prompt you send and every reply you get is written to a plain-Markdown file, timestamped, with the working time, token counts and an estimated dollar cost stitched onto each turn. Later you read that file — or ask for a one-line-per-turn total — to see what you did in a session and what it cost.

It works the same way across Claude Code, OpenCode and OMP. One command, /session-log, drives it everywhere; each tool keeps its own native storage and cost figures underneath.

What you get

  • A readable session transcript. Your prompts and the assistant's final replies, in order, each under an HH:MM:SS heading — a chronological diary of the session you can reread or grep.
  • Per-turn cost & timing. Every reply is followed by working time and an est. used token line: input, output, cache-write, cache-read, a total, and an estimated price.
  • Model / effort switch tracking. When you change model or reasoning effort between turns, a switched: line records it — worth noticing, because switching models resets the prompt cache and the next turn pays for a fresh cache write.
  • Sub-agent tracking. Each sub-agent that finishes adds a line naming it and pointing at its own transcript, so background work is visible and counted — even agents nested inside workflows.
  • Whole-session totals on demand. /session-log usage adds every turn and every sub-agent into one TOTAL — each transcript counted exactly once, however deeply nested.
  • Local and private. Logs are written under your home config directory with 600 permissions. Nothing is uploaded; pricing is computed offline from a checked-in table.

The four commands

Run /session-log with one of these. With no argument it defaults to status.

CommandWhat it doesTypical output
on Turns logging on for the current tool and wires it in. Claude Code: on — or on — restart required
off Turns logging off for the current tool. Claude Code: off
status default Reports whether logging is active right now. on / off / on — restart required / on — adapter missing
usage Prints a per-turn breakdown plus the session total. Claude Code: usage then the report

The label at the front of every line (Claude Code, OpenCode or OMP) tells you which tool answered. usage targets the newest session of the current project by default; pass a session id or a transcript path to total a specific one. On Claude Code, add --check to cross-check the total against ccusage when it is installed.

Good to know

  • Turn it on once, then restart. The first on installs the tool's logging hook. If status says on — restart required, restart the tool before relying on the log — the hook only takes effect in a fresh session.
  • On/off is per tool. Enabling it in Claude Code does not enable it in OpenCode or OMP; each keeps its own switch. status and off only ever touch the tool you are in.
  • Cost is an estimate. Hence est. — the price comes from a checked-in table, so it is deterministic and works offline, but it is not a bill. A model missing from the table contributes $0 and gets a ? so you can spot the gap.
  • The cache line is the interesting one. cache_create combines 5-minute and 1-hour cache writes (priced differently); a switched: line right above a large cache-write cost usually explains a spike.
  • The format is grep-friendly. ^### .* response$, ^est\. used token:, ^switched: and sub-agent finished: each match exactly one kind of line, so you can pull costs or responses out of a log with one command.
  • Dependencies. Needs bash, Python 3 and jq. usage additionally needs sqlite3 on OpenCode and Bun on OMP. A missing one gives a direct error.
  • Default locations only. Logs live under the standard home roots (e.g. ~/.claude/prompt-logs/). Relocated or custom config roots are unsupported and fail loudly rather than logging to the wrong place.

What a logged turn looks like

Scenario: one full turn — you submit a prompt, a background sub-agent finishes, the assistant answers, and you had switched model and effort since the previous turn. This is what lands in the session file (Claude Code, ~/.claude/prompt-logs/<project>/session_….md):

## 14:02:11

Implement the next uncompleted task in plans/FEAT-001.md

---

14:03:05 sub-agent finished: general-purpose (agent-9f3c2a1b), jsonl: /Users/…/<sid>/subagents/agent-9f3c2a1b.jsonl

### 14:05:53 response

<the assistant's final message, verbatim>

working time: 00:03:42
est. used token: input: 2000, output: 1000, cache_create: 150000, cache_read: 0, total_tokens: 153000, price: $2.32, model: claude-opus-5, effort: max
switched: model claude-sonnet-5 → claude-opus-5, effort high → max

---

Reading top to bottom: the prompt, then the sub-agent that ran, then the reply, then the measurements. total_tokens is input + output + cache-write + cache-read. The switched: line here explains the large cache_create: changing models forced a full cache write on this turn.

What a usage report looks like

Command: /session-log usage (totals the newest session of the current project).

Claude Code: usage

1. 14:02:11  Implement the next uncompleted task…   est. used token: … price: $2.32
2. 14:12:40  Fix the failing test in auth_test…      est. used token: … price: $0.41
   sub-agent general-purpose (agent-9f3c2a1b)         est. used token: … price: $0.77

TOTAL (2 requests, 1 sub-agent)  input: … output: … total_tokens: …  price: $3.50

One numbered line per turn, one line per sub-agent transcript found under the session, then a merged TOTAL. Every transcript is counted once, no matter how deeply sub-agents nest.
