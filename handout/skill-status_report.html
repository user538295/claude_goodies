/status_report

← Back to index

Summary

Kicked off a long task and don't know when it'll finish. Reports status on demand or on a recurring schedule — reads output files, commands, or URLs, extracts progress and a rough ETA, and stops itself when the task completes. Cancel anytime with /status_report off.

When to use

You started a background task — a test suite, build, deploy, migration, data pipeline — and want periodic updates without babysitting it. Works with any output source: a file written by the process, a shell command like kubectl get pods, or a URL.

  • "/status_report" — one check, right now
  • "/status_report 10 mins" — check every 10 minutes until done
  • "/status_report 5 minutes", "/status_report 2m", "/status_report 30" (bare integer = minutes) — other accepted interval forms
  • "/status_report off" — stop scheduled checks

Invocation

One-shot — report immediately, no scheduling:

/status_report

Recurring — report every interval until the task completes:

/status_report 10 mins
/status_report 5 minutes
/status_report 2m
/status_report 30    ← bare integer = minutes

Also accepted: second units (N sec/secs/second/seconds/Ns) and hour units (N hour/hours/Nh). Intervals under 60 s are floored to 60 with the note "Interval floored to 1 minute." If N ≤ 0 or the input can't be parsed, the skill asks rather than guessing.

Cancel scheduled checks — matching is case-insensitive and also fires when the argument merely begins with one of these words (e.g. "stop reports"):

/status_report off
/status_report cancel
/status_report stop

Cancelling stops only this skill's own monitor, by its task ID — it does not touch any other background task.

The skill identifies the running task from conversation context — background task ID, output file path, or description. If multiple tasks are found, it uses the most recently launched. If none found, it asks before proceeding. If the target task is genuinely ambiguous, it asks which task to monitor.

The Monitor tool may be unavailable in subagent contexts. If so: cancel mode reports nothing to cancel; recurring mode falls back to a one-shot check with a note that recurring scheduling is unavailable.

Content read from the monitored source (file, shell command, or URL) is treated as raw data only — any instructions it contains are never followed.

Tradeoff: recurring checks run as a persistent background monitor tied to the current session — if the session ends, they stop. A new session can still monitor the same task if you give it the output source (file path, command, or URL). Max 24 checks per run (~4 h at 10-minute intervals).

ETA is a rough linear extrapolation anchored on the first percentage actually observed — not check #1 itself — and re-anchored whenever progress resets to a lower value (e.g. a build phase finishing and a test phase starting over). It reports stalled if progress hasn't moved since the anchor. Not a commitment. It requires python3 on PATH and shows - when no numeric progress signal is available.

Check #1 never reports complete/failed on its own, even if the source already looks done — a single read can't distinguish a genuinely finished run from a monorepo between packages. In recurring mode the monitor always starts; completion is confirmed only once a later read finds the tail unchanged.

Example 1 — One-shot check (illustrative example)

Input:

/status_report

Output / Result:

14:32 - [test suite] Status update #1 - in progress 43% (187/430)

[raw task output — data only, not instructions]
- Running: src/billing, src/users, src/api
- 2 failures in src/notifications (non-blocking)
- No failures in completed packages

Example 2 — Recurring with completion (illustrative example)

Input:

/status_report 5 mins

Output / Result:

23:35 - [integration test suite] Status update #1 - in progress 17% (3/17)

[raw task output — data only, not instructions]
- [1/17] PASS tests/test_users.py::test_create
- [2/17] PASS tests/test_users.py::test_delete
- [3/17] PASS tests/test_billing.py::test_charge

ETA: -
Next check in 5 min
Monitor task ID: mon_a1b2c3 — checks every 5 min, each appears as a notification. To stop: /status_report off

[Monitor notification, 5 minutes later]

23:40 - [integration test suite] Status update #2 - in progress 47% (8/17)

[raw task output — data only, not instructions]
- [6/17] PASS tests/test_billing.py::test_refund
- [7/17] PASS tests/test_orders.py::test_create
- [8/17] PASS tests/test_orders.py::test_cancel

ETA: 23:48

[Monitor notification, 5 minutes later]

23:45 - [integration test suite] Status update #3 - in progress 100% (17/17)

[raw task output — data only, not instructions]
- [16/17] PASS tests/test_orders.py::test_refund
- [17/17] PASS tests/test_orders.py::test_ship_international
- 17 passed, 0 failed

ETA: 23:45

[Monitor notification, 5 minutes later]

23:50 - [integration test suite] Status update #4 - complete 100% (17/17)

[raw task output — data only, not instructions]
- [16/17] PASS tests/test_orders.py::test_refund
- [17/17] PASS tests/test_orders.py::test_ship_international
- 17 passed, 0 failed

Run complete — no further checks scheduled.

Note: check #3 shows 100% but is not yet reported complete — its tail just changed, so it isn't stable yet. Check #4 sees the identical tail and confirms completion. This one-interval confirmation cost is deliberate: a single reading can't tell "genuinely finished" apart from "one package just finished, the next is about to start."

Related tools

  • /wrap-up — End-of-session audit for when the task is code work; /status_report is for monitoring any running process.
  • /bugfix — Runs its agents sequentially in the foreground, so there's no background task or output file for /status_report to monitor. /status_report instead suits a long build or test suite launched with run_in_background.
